## Objective

Develop a strong conceptual understanding of Docker by learning **why** containers exist and how modern applications are deployed. Rather than memorising Docker commands, the focus this week was understanding the architecture behind images, containers, storage, networking and Docker Compose.

## Why Docker?

Before installing Docker, I explored the problem it was designed to solve.

I learned that containers exist to package applications together with everything they require to run, allowing software to be deployed consistently across different environments while consuming significantly fewer resources than traditional virtual machines.

Topics explored:

- Virtual Machines vs Containers
- Shared operating system kernels
- Resource efficiency
- Isolation
- Portability
- Reproducible deployments

This helped me understand that Docker is not simply another application, but a platform for consistently deploying software.

## Docker Architecture

One of the biggest concepts I learned was Docker's architecture.

```text
Docker Registry
        │
        ▼
Docker Image
        │
        ▼
Docker Container
```

### Docker Registry

I learned that Docker registries perform a similar role to Linux package repositories by providing:

- Trusted images
- Version management
- Image distribution
- Secure software delivery

### Docker Images

Rather than thinking of images as applications, I learned that an image is a **read-only blueprint** used to create containers.

Key concepts learned:

- Images are reusable.
- Images are immutable.
- Multiple containers can be created from a single image.
- Images remain on the system even after containers are removed.

### Docker Containers

I learned that containers are **running instances of images**.

Important concepts explored:

- Containers have a writable layer.
- Containers are isolated from one another.
- Containers share the host Linux kernel.
- Containers are intended to be disposable.

One of the most valuable lessons was Docker's philosophy of treating containers as **"cattle, not pets"**, meaning they should be recreated rather than manually repaired.

## Images and Containers

Using the `hello-world` image helped reinforce Docker's workflow.

I learned that Docker:

1. Checks whether an image already exists locally.
2. Downloads it only if required.
3. Creates a container from the image.

## Docker Volumes

One of the most important concepts I learned this week was persistent storage.

I explored why application data should remain separate from containers.

Key concepts:

- Docker volumes persist after containers are removed.
- Docker manages volume storage.
- Containers can be recreated without losing application data.

This reinforced Docker's philosophy that containers themselves should remain disposable.

---

## Bind Mounts

Compared Docker volumes with bind mounts.

I learned that bind mounts create a **live connection** between the host filesystem and the container.

Editing files on the Ubuntu server immediately updated the running application without rebuilding the container.

I also learned why:

- Bind mounts are commonly used during development.
- Docker volumes are preferred for persistent application data.

---

## Environment Variables

Explored how applications receive configuration.

I learned that Docker itself does **not** use environment variables.

Instead, Docker passes configuration values to the application when the container starts.

I also learned that changing environment variables requires creating a new container because applications normally read their configuration during startup.

## Troubleshooting Mindset

Throughout this week I continued following a structured administrative workflow.

**Inspect → Understand → Change → Verify**

Rather than immediately searching for commands, I focused on understanding:

- Where is the application running?
- Where is the data stored?
- Which network is being used?
- Is the issue related to the image, container, volume or configuration?
- How can I verify my assumptions before making changes?

This approach helped reinforce systematic troubleshooting rather than relying on trial and error.

## Reflection

This week completely changed how I think about deploying applications.

Instead of seeing Docker as a collection of commands, I now understand it as an ecosystem built around reusable images, disposable containers, persistent storage, networking and declarative infrastructure.

One of the most valuable lessons was recognising that modern infrastructure is designed to be reproducible. Rather than manually configuring servers, Docker encourages describing the desired state of an application and recreating it consistently whenever required.

Completing Docker fundamentals has prepared me to move beyond isolated concepts and begin building a production-style homelab using real services such as Homepage, Portainer, Uptime Kuma, Vaultwarden, AdGuard Home and Nginx Proxy Manager. Those projects will reinforce the concepts learned this week while providing practical experience that I can demonstrate and discuss in technical interviews.
